## How the F-Droid pipeline works for Ticklr

- **Reproducible, dev-signed** (decided in TIC-101): F-Droid builds
  `assembleRelease` from the tagged commit (unsigned — the signing config only
  attaches when keystore credentials are present), strips the signature from
  our published APK, verifies the two match byte-for-byte, then distributes
  **our** signed APK. Users get a binary provably built from this source.
- `Binaries:` points at the GitHub Release asset `ticklr-v<x.y.z>.apk`, which
  `.github/workflows/android-release.yml` uploads on every release tag.
- **After the initial submission is merged:**
  `UpdateCheckMode: Tags ^android/v[0-9.]+-production$` lets F-Droid poll our
  production tags; `AutoUpdateMode: Version` opens their version-bump MRs
  automatically. Nothing extra to do per release beyond the normal tag flow,
  as long as the version-bump PR keeps `versionCode`/`versionName` literals
  accurate (CI enforces the tag ↔ versionName match).
- App listing text/icon comes from `fastlane/metadata/android/` in this repo
  (generated by `scripts/sync-fdroid-metadata.py` — regenerate after any Play
  listing or release-notes change, before tagging).

## Reproducibility invariants (do not break)

- `versionCode` / `versionName` stay **plain literals** in
  `android/app/build.gradle.kts`.
- `dependenciesInfo.includeInApk = false` stays — the Google-encrypted "SDKP"
  blob is nondeterministic and F-Droid rejects opaque blobs.
- The release signing config attaches only when credentials are present
  (`.takeIf { it.storeFile != null }`) so credential-less builds produce an
  unsigned APK instead of failing.
- Verified 2026-08-13: two clean `assembleRelease` runs are byte-identical
  (AGP 8.x / JDK 21). Re-verify after AGP/Kotlin upgrades:
  build twice with `clean` between, `cmp` the APKs.

## Submission checklist (first-time, item 7 of TIC-101)

1. Land all prep on `main`; cut the first post-prep release
   (`android/v1.12.2-production`, versionCode 133) — every earlier tag
   predates the literal-version/reproducibility work and cannot be built by
   F-Droid.
2. Confirm the GitHub Release exists with `ticklr-v1.12.2.apk` attached.
3. Add `AllowedAPKSigningKeys: <sha256>` to the yml — certificate digest of
   the release key:
   `keytool -list -v -keystore ~/Documents/ticklr-release.keystore -alias ticklr`
   (SHA-256 line, lowercase hex without colons), or from the published APK:
   `apksigner verify --print-certs ticklr-v1.12.2.apk`.
4. Fork fdroiddata on GitLab, branch `com.xaymaca.sit`, add
   `metadata/com.xaymaca.sit.yml`, run `fdroid lint com.xaymaca.sit` (clean as
   of 2026-08-13 except the AllowedAPKSigningKeys advisory, which step 3
   resolves).
5. Optionally test the full build in fdroidserver's Docker/vagrant builder, or
   push and let fdroiddata's GitLab CI validate.
6. Open the MR with the `New App` label; respond promptly to reviewer
   questions. Expect ~24–48h after merge before the app appears (human APK
   signing verification on their side).
